# 遊戲知識規劃與蒐集前置流程

本流程的 PEAK 第一批實作已落地：[遊戲分析](peak-core-plan.md) 與 [ssr.game-plan.v1](../plans/peak-core-v1.json)。保存端會驗證計畫、欄位和關聯，並從 DB 顯示本批實際覆蓋及缺漏；下文原先「未自動執行」描述的是規劃分析本身，不是目前保存端的驗證能力。

[攀登與生存續批](peak-survival-plan.md)將同一 DB 擴充至 41 筆。[補給與區域行程續批](peak-expedition-plan.md)再新增 30 筆、補強 7 筆；目前共 71 筆，均已實際保存、讀回及畫面核對。

規劃唯一入口：[issue #1](https://github.com/HGPT-StreamSuite/ssr-collector-peak/issues/1)。流程已由使用者確認；實際遊戲的分類與目標仍需逐案分析，不能把現有 PEAK 盤點視為最終分類已獲批准。

核心完成條件：**先分析要存什麼，A 擷取後輸出共同檔案，B 整理並實際保存待審知識修訂，C 直接查同一個指定 DB 供使用者驗收。** 找到補充資料後，查證紀錄與待辦只是進度；必須完成保存及讀回，才能將該筆列為已完成。

## 固定流程，依遊戲決定內容

1. **遊戲名稱 → 根條目／分析任務**：固定識別與版本／平台，理解核心玩法、遊戲結構及 DB 要回答的問題。
2. **決定適用知識類型**：考慮遊戲介紹、評價、官方更新公告，以及該遊戲實際存在且有用的角色、道具、模式、機制、狀態、區域、生物、攻略與故事世界觀。不強制每個遊戲採相同分類。
3. **自己的條目／欄位／關聯計畫**：列具體目標、識別與別名、適用版本、所需欄位／單位、關聯方向與角色、優先順序、可驗收問題、已知缺口。網站導覽只能協助找來源，不能直接作為 DB taxonomy。
4. **來源對應**：每個目標對上精確來源與詳細段落、表列、官方文字 key；分清官方事實、Wiki、分析、玩家實測與評價。含糊集合或「某道具」需循獲准的詳細來源釐清，不能猜補。
5. **受限擷取 → 收納／整理保存 → 查詢顯示**：各環節獨立執行並以檔案交接；逐項保留證據與狀態。

根分析至少產出：遊戲結構／問題清單、適用知識類型及排除理由、具體條目／欄位／關聯目標、來源對應與下一批有界目標。這是規劃產物，不表示任何內容已被蒐集或入庫；目前程式未自動執行或強制此規劃流程。

## 每個遊戲的規劃交付物

以下是逐案分析的必要內容，不是所有遊戲共用的固定分類表。PEAK 已實作的新 JSON schema 與具體目標見上述計畫：

1. **根分析**：遊戲識別、平台／版本、基本玩法與目標、遊戲的主要構成，以及使用者要向 DB 提出的具體問題。未知事項明列，不能用網站目錄代替分析。
2. **自己的分類**：逐項判斷介紹、評價、更新，以及角色、道具、模式、機制、攻略、世界觀等是否適用；記錄納入／排除理由、條目粒度與分類間的界線。網站分類另保留為來源對照，不自動決定我們的分類。
3. **條目與欄位**：為本批目標列出穩定識別、名稱／別名、要回答的問題、欄位語意、值的型別與單位、版本／日期，以及來源未提供時的缺漏表示。介紹、評價與更新的內容要求見下節。
4. **關聯**：列明起點、終點、方向、關聯語意及逐項證據需求；先確認目標條目是否存在。官方顯示條件、攻略建議、前置物品集合、多人計入與獎勵分開，不用一種關聯冒充另一種。
5. **來源與驗收對照**：每個欄位／關聯對應精確來源位置、取得方式、適用日期／版本、優先順序及驗收查詢；指定要保存並讀回的 DB。尚未找到來源、取得受阻及程式尚不支援分開記錄。

規劃有修訂時保留變更原因與版本；新增分類或欄位若超出接收／保存能力，先在原 issue／PR 記錄並補齊支援，不能默默塞進不相符的分類或丟棄欄位後宣稱完成。

## 介紹、評價、更新

- **介紹**保留玩法、目標、結構、平台／版本與來源；沒有可靠資料的故事世界觀保留缺口，不採同人補寫。
- **評價**保留作者、來源、日期、適用版本（有提供時）、立場及理由；主觀結論與可核對事實／機制分開，不冒充官方。
- **官方更新公告**保留原公告、發布日期與版本／build（有提供時），對應哪些既有條目／欄位受影響。更新以新證據／新修訂保留歷史，不能抹去舊版或自行消解來源分歧。

## 內容欄位是分析後的候選

道具可規劃：原文／表列、效果數值與單位、用途、取得地點／方式、使用步驟、限制、烹調變化與徽章關聯；名稱沿用可追溯的官方英文／繁中，其他譯名另標。

徽章可規劃：官方顯示條件，與 Wiki 攻略的前置、明確物品集合、步驟、多人計入、獎勵、限制及版本分開。機制、狀態、區域、生物、攻略同樣按遊戲分析決定欄位。不要求每個來源都提供每個欄位。

規劃目標、已找到、已擷取、文件已收納、知識修訂已保存、已顯示、查詢已驗證分開記錄。來源未提供、取得失敗／受限、驗證拒收、找到未存、已存未顯示不能混為同一種「缺少」。

## 三個獨立責任與驗收

- A：自有標準 collector 或另外開發的客製擷取程式，取得有權使用的原文，輸出同一[檔案契約](file-handoff.md)；不寫 knowledge DB。
- B：knowledge 獨立驗證／保存文件，再以逐項原文證據建立 pending-review 知識修訂；不自動批准或發布。官方顯示文字與 Wiki 攻略／關聯保留不同來源。
- C：**輸入查詢條件 → 直接查指定資料庫 → 顯示實際查詢結果**。測試、報告與驗收頁本身應實際完成此流程。真實資料查指定持久 DB；合成模式明確選定實際保存的測試 DB。

實際寫入結果 → 新程序／新 DB 連線讀回 → API → 實際頁面，逐筆核對內容、revision、來源及關聯。只有文件快照、合成 exit 0、空查詢、靜態摘要或 UI 修正不足以完成真實知識驗收。三段不要求同程序、共享套件或服務綁定，也不串接聊天流程。

## 固定執行順序與完成判定

1. 完成上方根分析與本批目標，確認來源及保存端目前能表示哪些欄位／關聯。
2. A 依本批目標取得內容，保留原文及來源觀測，輸出 `ssr.collection.v1`。標準與客製 collector 使用同一份接收契約，各自保留 producer 身份；A 可獨立結束，不需 B 或 C 在線。
3. B 讀取檔案，驗證後明確保存來源文件；再從已保存原文整理條目、欄位及關聯，以自己的草稿匯入流程實際寫入指定 DB。**文件保存只是 B 的第一步；只有 snapshot／receipt，仍未完成知識保存。**
4. B 完成寫入後結束該次寫入連線，以新程序讀回每筆 entry／revision、內容、來源及關聯。重複資料維持去重，新增補充／更新保留舊修訂；新內容存為 `pending_review`，不順便批准或發布。
5. C 接收查詢條件，重新讀取步驟 3 的同一 DB，顯示實際結果與資料庫身份供使用者親自驗收。每筆都須與步驟 4 一致；測試頁／報告頁就是此查詢功能，不能另以手寫摘要、先前匯出 JSON 或另一個 DB 補答案。

進度至少分開記錄「已規劃」「找到未擷取」「已擷取未收納」「文件已存但知識未存」「知識已存未顯示」「已讀回並查詢顯示」；受阻原因另記來源未提供、取得失敗／受限或驗證拒收。這些是驗收要求，目前沒有宣稱程式已自動維護完整進度帳。

若本輪已找到可使用的補充內容，執行者應沿步驟 3–5 完成保存與讀回；遇到真實阻塞才保留精確原因與最後完成階段，不以新增待辦取代可完成的寫入。接收／保存命令、逐筆證據與尚未支援能力以 [knowledge 保存與查詢驗收規格](https://github.com/HGPT-StreamSuite/ssr-knowledge/blob/codex/peak-local-collection/docs/persistence-and-query-acceptance.md) 為準。
