# 遊戲知識規劃與蒐集前置流程

規劃唯一入口：[issue #1](https://github.com/HGPT-StreamSuite/ssr-collector-peak/issues/1)。流程已由使用者確認；實際遊戲的分類與目標仍需逐案分析，不能把現有 PEAK 盤點視為最終分類已獲批准。

## 固定流程，依遊戲決定內容

1. **遊戲名稱 → 根條目／分析任務**：固定識別與版本／平台，理解核心玩法、遊戲結構及 DB 要回答的問題。
2. **決定適用知識類型**：考慮遊戲介紹、評價、官方更新公告，以及該遊戲實際存在且有用的角色、道具、模式、機制、狀態、區域、生物、攻略與故事世界觀。不強制每個遊戲採相同分類。
3. **自己的條目／欄位／關聯計畫**：列具體目標、識別與別名、適用版本、所需欄位／單位、關聯方向與角色、優先順序、可驗收問題、已知缺口。網站導覽只能協助找來源，不能直接作為 DB taxonomy。
4. **來源對應**：每個目標對上精確來源與詳細段落、表列、官方文字 key；分清官方事實、Wiki、分析、玩家實測與評價。含糊集合或「某道具」需循獲准的詳細來源釐清，不能猜補。
5. **受限擷取 → 收納／整理保存 → 查詢顯示**：各環節獨立執行並以檔案交接；逐項保留證據與狀態。

根分析至少產出：遊戲結構／問題清單、適用知識類型及排除理由、具體條目／欄位／關聯目標、來源對應與下一批有界目標。這是規劃產物，不表示任何內容已被蒐集或入庫；目前程式未自動執行或強制此規劃流程。

## 介紹、評價、更新

- **介紹**保留玩法、目標、結構、平台／版本與來源；沒有可靠資料的故事世界觀保留缺口，不採同人補寫。
- **評價**保留作者、來源、日期、適用版本（有提供時）、立場及理由；主觀結論與可核對事實／機制分開，不冒充官方。
- **官方更新公告**保留原公告、發布日期與版本／build（有提供時），對應哪些既有條目／欄位受影響。更新以新證據／新修訂保留歷史，不能抹去舊版或自行消解來源分歧。

## 內容欄位是分析後的候選

道具可規劃：原文／表列、效果數值與單位、用途、取得地點／方式、使用步驟、限制、烹調變化與徽章關聯；名稱沿用可追溯的官方英文／繁中，其他譯名另標。

徽章可規劃：官方顯示條件，與 Wiki 攻略的前置、明確物品集合、步驟、多人計入、獎勵、限制及版本分開。機制、狀態、區域、生物、攻略同樣按遊戲分析決定欄位。不要求每個來源都提供每個欄位。

規劃目標、已找到、已擷取、文件已收納、知識修訂已保存、已顯示、查詢已驗證分開記錄。來源未提供、取得失敗／受限、驗證拒收、找到未存、已存未顯示不能混為同一種「缺少」。

## 三個獨立責任與驗收

- A：自有標準 collector 或另外開發的客製擷取程式，取得有權使用的原文，輸出同一[檔案契約](file-handoff.md)；不寫 knowledge DB。
- B：knowledge 獨立驗證／保存文件，再以逐項原文證據建立 pending-review 知識修訂；不自動批准或發布。官方顯示文字與 Wiki 攻略／關聯保留不同來源。
- C：**輸入查詢條件 → 直接查指定資料庫 → 顯示實際查詢結果**。測試、報告與驗收頁本身應實際完成此流程。真實資料查指定持久 DB；合成模式明確選定實際保存的測試 DB。

實際寫入結果 → 新程序／新 DB 連線讀回 → API → 實際頁面，逐筆核對內容、revision、來源及關聯。只有文件快照、合成 exit 0、空查詢、靜態摘要或 UI 修正不足以完成真實知識驗收。三段不要求同程序、共享套件或服務綁定，也不串接聊天流程。
